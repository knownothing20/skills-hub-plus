# Skills Hub 技能同步（`skill-hub-sync`）

## 这个 skill 要解决的问题

用户经常在**别的软件里**改 skill（Codex、Claude Code、WorkBuddy、豆包、Gemini…）。
改完之后他不想再手动点 GUI、逐个卡片对比谁新，只想说一句「同步一下」，
让改动精准地铺到所有位置 —— **包括母库**。

本 skill 就是这件事的操作手册。原则只有一条：

> **不猜方向，不猜内容。** 谁能确定唯一最新版本才动手；多份各改各的，
> 停下来让人选。绝不因为「时间新」就覆盖掉别人的改动。

---

## 一、先认清「位置」有几种

同步的对象**不是「副本集合 + 一个主 skill」**，而是**平级的多份内容 + 一份基线**：

| 位置 | 在哪 | 是否在 `skill_targets` 表 |
| --- | --- | --- |
| **母库** | 仓库下的 `skills\<技能名>`（路径以库里 `skills.central_path` 为准，**不要写死**） | **不在**（关键） |
| 各软件副本 | `~/.codex/skills/<名>`、`~/.claude/skills/<名>`、`~/.workbuddy-ai/skills/<名>`、豆包 `Profile N` … | 在 |

母库不在 `skill_targets` 表里，所以**任何只遍历这张表的代码都看不见母库**。
历史上这正是「在别的软件改完，母库一直不更新」的根因。2.0.4 起已经修掉：
`reconcile_skill`、`scan_peers` 都把母库当一等参与者，显示名为 `母库`。

> **不要**再写「先同步副本，再单独手工补母库」这种两步流程。现在是同步一次、
> 母库和副本一起处理。

---

## 二、怎么干：本技能自带工具，不依赖 CLI

### 2.1 `sync.py` —— 首选，一条命令干完

本技能目录里的 `sync.py` 就是完整的同步工具，**读的是同一个数据库、同一套规则**，
不需要 `skills-hub-cli.exe`。

**关键：不要硬编码别的软件的路径。** 本技能在 10 个位置各有一份完整副本
（母库 + 各软件），**在你当前软件里，就用你当前读到的这一份**：

```bash
# 先确认自己在哪（各软件路径不同）
ls ~/.codex/skills/skill-hub-sync/sync.py          # codex
ls ~/.claude/skills/skill-hub-sync/sync.py         # claude code
ls ~/.workbuddy-ai/skills/skill-hub-sync/sync.py   # workbuddy
ls ~/.gemini/config/skills/skill-hub-sync/sync.py  # antigravity
ls ~/.zcode/skills/skill-hub-sync/sync.py          # zcode
ls ~/.workbuddy/skills/skill-hub-sync/sync.py      # workbuddy（旧）
# 豆包：.../User Data/<Profile>/.doubaowork/agent_mode/workspace/.user_skills/skill-hub-sync/
```

找到哪个存在就用哪个，**它们在功能上完全等价**（字节级一致）。下面的例子统一写成
`SYNC`，你按上面实际找到的路径填：

```bash
SYNC="py $HOME/.codex/skills/skill-hub-sync/sync.py"   # 例：在 codex 里就这样
```

> ⚠️ **不要**写死 `~/.workbuddy-ai/...` 去在 codex 里用——那个目录在 codex 视角
> 下可能不存在（不同软件的用户目录不同）。用**自己所在软件**的那一份最稳。

**Python 命令名按环境挑**（三者等价，脚本兼容 3.10–3.13）：

| 环境 | 用哪个 | 说明 |
| --- | --- | --- |
| Windows（装了 py launcher） | `py` | 最稳，多个版本都在 |
| PATH 里有 python | `python` | — |
| macOS / Linux | `python3` | — |

先跑 `py -V`（或 `python3 -V`）确认能用，再往下走。**只用标准库**，
不需要 pip 装任何东西。

| 命令 | 作用 | 写文件？ |
| --- | --- | --- |
| `sync.py status` | 列出每个技能各位置**相对基线**的状态 | ❌ 只读 |
| `sync.py status <关键字>` | 同上，只看某个技能 | ❌ 只读 |
| `sync.py status --json` | 机器可读 | ❌ 只读 |
| `sync.py diff <技能>` | 具体哪些文件不同（+新增 / -缺失 / ~改动） | ❌ 只读 |
| `sync.py pull` | 收回：唯一偏离基线的那份 → 其它所有位置（**含母库**） | ✅ |
| `sync.py push` | 推出：母库 → 全部副本 | ✅ |
| `sync.py adopt <技能> --from <位置>` | 指定以某位置为准 | ✅ |
| 任意写操作加 `--dry-run` | 只打印计划 | ❌ |

**永远先跑 `status`**（只读、安全），看清结论再决定动不动手。

### 2.2 `status` 会给你四种结论，含义完全不同

| 结论 | 含义 | 该做什么 |
| --- | --- | --- |
| 可同步（只有一份偏离基线） | 某处改了，别处没跟上 | `pull`（或 `push`，方向由你定） |
| ⚠️ 冲突（多份各改各的） | 多个软件各改各的，**没有唯一最新** | 先 `diff` 看差异，再用 `adopt` 指定 |
| ℹ️ 基线过期（各位置其实一致） | 内容早就一致，只是数据库基线旧了 | `pull` 会**只刷新基线，不复制任何文件** |
| ℹ️ 尚无基线 | 第一次见这个技能，各位置内容还互不相同 | `adopt` 指定以谁为准 |

后两种是我在实际使用中发现的真实情况——它们**看起来像「需要同步」，其实不需要**。
如果分不清，「基线过期」会被误当成差异，把本来就一致的内容再覆盖一遍（还会
白白搬一次目录进回收站）。

### 2.3 收回改动（最常用）

```bash
$SYNC pull                # 全库
$SYNC pull <关键字>       # 只处理名字含该关键字的技能
$SYNC pull --dry-run       # 先看要做什么
```

语义是：**每个技能跑一次对等比对**。

| 情况 | 行为 |
| --- | --- |
| 只有一份内容偏离基线 | 采纳它，铺到母库和其余所有位置 ✅ |
| 多份偏离且内容不同 | **停下报告冲突**，一个字节都不写 ⚠️ |
| 偏离的那份命中历史版本 | 判为「回滚」，不扩散 ⏭️ |
| 各位置已一致、只基线旧 | 只刷新基线，不动任何文件 ⟳ |
| 全部与基线一致 | 不动 |

> 注意没有「文件数超过 500 就跳过」这条：`sync.py` 与 Rust 侧目前并不一致
> （Rust 有这道闸，Python 没有）。遇到文件数特别大的技能，先 `status` 确认
> 内容是否真的都该同步，别盲目铺开。

### 2.4 冲突时：先看差异，再指定以谁为准

```bash
$SYNC diff <技能名>
```

逐个文件列出 `+ 新增` / `- 缺失` / `~ 内容不同`。看完再决定：

```bash
# 以某份副本为准，推到母库和其余所有位置
$SYNC adopt <技能名> --from codex

# 多账号软件的实例带 #编号（与 status 里显示的写法一致）
$SYNC adopt <某技能> --from "doubao_work#Profile 2"

# 以母库为准（最保守：撤掉副本的改动，恢复母库那一版）
$SYNC adopt <技能名> --from 母库
```

`adopt` **会同时更新母库**。源本身就在母库时会跳过母库（否则自己覆盖自己）。

### 2.5 只想把母库推出去

```bash
$SYNC push              # 母库 → 所有内容不一致的副本
```

与 `pull` 方向相反：`push` **不采纳**副本改动，只修「母库更新了、副本没跟上」。

### 2.6 改了技能想立刻在别的软件生效

技能是**启动时读取**的，已在运行的会话不会热重载，需要新开一个对话。

### 2.7 如果有 `skills-hub-cli.exe`（可选）

装了软件的话，`skills-hub-cli` 是同一套逻辑的 Rust 实现，命令名基本相同
（`status` / `pull` / `push` / `diff` / `adopt`），可以任选其一。
**两者不要同时用编辑同一批文件**，选一个。没有 CLI 时 `sync.py` 完全够用。

## 三、什么时候必须停下来问用户

自动动手之前，只要命中任何一条，**先问**：

1. **输出里有「各改各的」/ 冲突** —— 让它用 `diff` 看完再 `adopt` 指定。
2. **要覆盖的方向与用户说的相反** —— 用户说「以 Codex 的为准」，而 `status`
   显示的 A（最新）是豆包，先确认，别自作主张按时间推。
3. **技能里带私有目录**（`local/`、`logs/`、`runtime/`）—— 见 5.1，先确认规则。
4. **涉及含凭据的目录** —— 例如 `<某技能>` 的
   `local/gateway.dpapi` 是 codex 专属加密凭据，**绝不能**扩散到别的软件。
   这类差异不是「不一致」，是有意为之。
5. **`status` 显示某个技能全部位置都一致，但用户说某处改过** —— 那多半是
   改了 `.skillignore` 命中项（私有内容本来就不参与比对）。先解释清楚。

## 四、手工流程（`sync.py` 也不可用时的最后兜底）

先说清楚：**正常情况下不该走到这一节**。`sync.py` 已经在实测中完整验证过
`status` / `pull` / `push` / `adopt` 四条链路（母库回流、冲突不动手、
私有内容不扩散都验过）。只有当 Python 不可用、或技能文件本身丢了的时候，
才按下面手工做——核心是**先备份、再比对、只写确定的方向**。

### 4.1 定位数据库与母库

```bash
DB="$APPDATA/io.github.mcncarl.skillshub/skills_hub.db"
```

母库路径**从数据库读**，不要写死（仓库可能 clone 到任何地方）：

```bash
sqlite3 "$DB" "select name, central_path from skills where name='<技能名>'"
```

### 4.2 列出一个技能的所有位置

```bash
python - <<'PY'
import sqlite3, os
db = os.path.expandvars(r'%APPDATA%\io.github.mcncarl.skillshub\skills_hub.db')
c = sqlite3.connect(db)
sid = c.execute("select id from skills where name=?", ('<技能名>',)).fetchone()[0]
for tool, inst, path in c.execute(
    'select tool,instance,target_path from skill_targets where skill_id=?', (sid,)):
    print(f'{tool}#{inst or "-"}\t{path}')
PY
```

### 4.3 比对内容（应用 `.skillignore`！）

**绝对不能**直接 `diff -r`：会把 `local/` 这类各软件私有内容算成差异，
进而误判、误覆盖。必须排除 `.skillignore` 里列出的路径：

```bash
# 先看规则（用 $HOME，不要写死用户名）
cat "$HOME/.codex/skills/<技能名>/.skillignore"

# 比对时排除（示例：local、logs、runtime、node_modules）
diff -r -x local -x logs -x runtime -x node_modules \
  "<母库>/<技能名>" "$HOME/.codex/skills/<技能名>"
```

### 4.4 备份（按「位置名」命名，不要按目录名）

```bash
BK=~/.workbuddy-ai/skill-sync-backup/$(date +%Y%m%d-%H%M%S)-manual
mkdir -p "$BK"
cp -a "<母库路径>/<技能名>" "$BK/母库"
cp -a "$HOME/.codex/skills/<技能名>"        "$BK/codex"
# 多账号软件带实例名，否则几个 Profile 撞成同名
cp -a "$HOME/AppData/Local/DoubaoWork/User Data/Profile 2/.doubaowork/.../<技能名>" \
      "$BK/doubao_work-Profile-2"
```

**为什么不能直接 `cp` 目录原名**：同名的 `<技能名>` 会在备份里撞成
`<技能名>`、`<技能名>-1`、`<技能名>-2`，事后根本分不清哪个对应哪个软件。
必须按位置标签命名，并写一份 `MANIFEST.txt` 记下「备份目录 → 原位置」。

这一步不能省。

### 4.5 同步（只有整目录复制一种方式）

```bash
# 用 cp -a（保 mtime）；不要用 rsync（这台机器上没装）
cp -a "源目录/." "目标目录/"
```

**私有内容必须人工保护**：覆盖前先把目标目录里的 `local/`、`logs/` 等
搬到临时位置，复制完再搬回去；或者先确认这些路径都在 `.skillignore` 里。
否则它们会被清掉（2026-11 一次真实事故的根因——8 份配置就是这么丢的）。

`sync.py` 的 `replace_dir()` 做的就是这件事（`preserve_entries` → 复制 →
`restore_entries`），手工做时务必照着这个顺序。

### 4.6 复检

比对**所有**位置（含母库），确认 0 处差异，再把结果报告给用户。

## 五、几个必知的坑（全是真实踩过的）

### 5.1 `.skillignore` 决定什么算「私有内容」

在 `DEFAULT_IGNORES` 和 `.skillignore` 里的路径：

- 不参与内容比对（所以改了它们 `status` 看不出差异）；
- 不参与整目录复制（所以不会被覆盖）；
- 但**整目录替换前会被搬出来、复制后搬回原位**，靠的正是这份规则。

规则缺失的后果很重：母库如果没有 `.skillignore`，而副本有，那副本的
`local/`（配置、日志、凭据）会被当成**技能内容**复制进母库；
反过来也一样。所以**规则必须先对齐，再同步内容**。

### 5.2 `local/` 每个软件独立，不许共享

`local/` 放的是该软件自己的连接配置、token、运行态。同步它等于把 A 软件的
凭据发给 B 软件。遇到这类目录，默认**不扩散**。

### 5.3 「时间新」不等于「该覆盖」

对等模型的第一原则是内容哈希，不是 mtime。拷贝、还原备份、编辑器保存都会
刷新 mtime。判断方向只看：**哪一份偏离基线，以及偏离的是不是只有一份**。

### 5.4 回滚不扩散

如果某份内容回到了过去出现过的版本，系统判为「回滚」并跳过。这是保护：
把旧版本铺满全库是灾难。遇到 `Rollback` 要提醒用户「这是往回退，需你确认」，
不要绕过去。

### 5.5 单副本技能最容易出问题

只有一份副本的技能（例如 `<技能名>` 早期只有 workbuddy_ai 一份），
如果同步逻辑只看副本表，母库就永远收不到更新。**确认母库在比对范围内**是
每次同步都该做的检查，`sync.py status` 输出里「母库」那一行就是做这个用的。

## 六、标准操作流程（照这个顺序做）

```bash
# SYNC = 你当前软件里那份（见 2.1 的路径清单），例：
SYNC="py $HOME/.codex/skills/skill-hub-sync/sync.py"
```

1. **问清意图**：「你是要收回别处的改动，还是要把母库推出去？」
   - 收回 → `pull`；推出 → `push`；不确定 → 先 `status`
2. **`status` 先看**（只读），把结论告诉用户：哪个位置偏离、偏离了几个文件。
3. **判断是否需要问**：命中第三节任一条 → 停下来问，不要自作主张。
4. **干跑**（重要技能）：`pull --dry-run`。
5. **执行**：`pull` / `push` / `adopt`。
6. **复检**：再跑 `status`，确认目标技能已消失（「都与基线一致」）。
7. **报告**：改了哪些技能、多少个位置、**母库是否更新**、
   备份在哪、哪些被跳过及原因。

第 7 步里的「母库是否更新」必须单独确认——这是用户最在意的一条，
光看副本之间一致是不够的。

## 七、常见问答

**Q：`status` 什么都没显示，是不是坏了？**
A：它只列「需要处理」的技能。全部一致时就是一句「全部 N 个技能都与基线一致」。

**Q：`status` 说「基线过期」是什么意思？是我弄坏了吗？**
A：不是。它的意思是**各位置内容其实已经完全一致**，只是数据库里的基线记录
还停在旧版本（常见于刚把同一份内容分发到所有位置之后）。`pull` 会只刷新基线，
**不复制任何文件**，可以放心跑。

**Q：`status` 说「尚无基线」呢？**
A：这个技能是第一次被这套工具看到。如果各位置内容已经一致，`pull` 会直接
建基线；如果各位置内容互不相同，它会拒绝动手，要你用 `adopt` 指定以谁为准。

**Q：`pull` 说「采纳自 母库」是什么意思？**
A：唯一偏离基线的那份是母库，所以把母库的内容推给副本。这是正常结果。

**Q：能不能只同步一个软件？**
A：`pull <技能名>` 只能限定技能，不能限定目标软件。只推一个方向用 `push`
（母库 → 全部副本）或 `adopt`（某位置 → 全部其它位置）。
「只给某一个软件单独发一版」不属于同步，属于有意制造不一致，**不要做**。

**Q：备份在哪？**
A：`~/.workbuddy-ai/skill-sync-backup/<时间戳>-<动作>/`，里面有按位置命名的
子目录（`母库`、`codex`、`doubao_work-Profile-2`…）和一份 `MANIFEST.txt`
记录每个备份目录原本对应哪个位置。**出问题按 MANIFEST 还原，别凭目录名猜。**

**Q：改了技能想立刻在别的软件生效，要重启那个软件吗？**
A：技能是启动时读取的，已在运行的会话不会自动重载，需要新开对话。

## 八、红线

1. **不猜内容**：没读到文件就不许说「应该是这样」。
2. **不按 mtime 决定方向**：方向只由基线决定，基线失效时停下来问。
3. **不把 `local/`、`logs/`、凭据扩散到别的软件**。
4. **覆盖前先备份**，备份必须按**位置名**命名并留 `MANIFEST.txt`
   （同名技能在多个软件里都叫同一个名字，按目录名备份必然撞车）。
5. **不手动改 `skill_baselines` 表**。基线由 `sync.py` / CLI 维护；手改会让
   「基线过期」和「真的有人改了」混在一起，再也判断不出方向。
6. **不动母库以外的东西**：`dist-app/`、`skills/`、`package.json`、`.git`
   是便携版的定位锚点，严禁挪动重命名。
7. **用户说「看一下 / 分析」就是只读**，只跑 `status` / `diff`，不许 `pull`。
8. **`sync.py` 与 `skills-hub-cli` 不要同时操作同一批文件**，选一个。

## 九、这个 skill 自己的能力边界（诚实说明）

已经实测验证过的：

- ✅ `codex` 改完 → `pull` → **母库内容真的更新了**（不是只改副本）
- ✅ 多份各改各的 → 判冲突，**一个字节都不写**，两份内容原样保留
- ✅ `adopt --from claude_code` → 母库和另一副本都跟着变
- ✅ `push` → 母库推出到全部副本
- ✅ 全程三处的 `local/cfg.json` **各自保留原值**（没扩散、没被清掉）

**尚未对齐 Rust 的地方（用之前要知道）**：

- `sync.py` 没有「文件数超过 500 就跳过」的闸（Rust 侧 `MAX_FILES_PER_SKILL`
  有）。文件特别多的技能请先 `status` 确认，别盲目铺开。
- `sync.py` 没有「连续两轮确认」机制（Rust 侧 `require_stable` 在 GUI 里才有，
  CLI 也是传 `false`）。所以编辑器存盘存到一半时跑 `pull`，可能收进半成品。
  **改完稍等一下再同步**。

### 复制到别的软件 / 别的机器能用吗

**能直接用，但前提是这个技能已经被 Skills Hub 登记过。**

实测：把本技能目录复制进第三个软件目录，从那里执行 `pull`，
母库和另一个软件都收到了改动——**不依赖装在哪里**。

但方向判断靠数据库里的基线，所以：

| 情况 | 表现 |
| --- | --- |
| 数据库存在且登记过该技能 | 正常工作 |
| 数据库存在但没登记该技能 | 显示「0 个技能」，**什么都不做** |
| 数据库文件不存在 | 报「找不到数据库」退出 |
| 想在没有 Skills Hub 的机器上用 | 只能按第四节**手工**同步，方向由人定 |

这不是缺陷，是「不猜方向」的必然结果：**没有基线就没有权威版本**，
机器无法知道该往哪个方向铺。所以「拷过去就能用」的准确说法是
「拷过去、且在目标机器上跑过 Skills Hub 并扫描过，就能用」。
